# NeonKey Pay

Отдельный сервис (Vercel) для приёма крипто-платежей (USDT-TRC20, TRX,
TON) в пополнение баланса основного NeonKey Mini App. Работает через
one-time адреса, детерминированно выведенные из одного seed — деньги
остаются под полным контролем, без сторонних платёжных агрегаторов.

## Что уже готово

- ✅ Деривация TRON-адреса по индексу (`lib/wallets/tron.ts`) — общий для USDT-TRC20 и TRX.
- ✅ Деривация TON-адреса через `walletId` (`lib/wallets/ton.ts`).
- ✅ Проверка подписи Telegram `initData` (`lib/telegramAuth.ts`) — для
  реальных вызовов из Mini App.
- ✅ Внутренний токен-доступ (`lib/auth.ts`) — для дашборда и фонового воркера.
- ✅ Курс, комиссия (₽ фиксированная либо % от суммы) и минималка пополнения
  берутся из той же таблицы `settings`, что и в основном Mini App
  (`lib/rates.ts`) — настраиваются прямо из существующей админки, отдельная
  админка для этого сервиса не нужна.
- ✅ `POST /api/payments/create` — создаёт депозит, фиксирует курс/комиссию, выводит адрес.
- ✅ `GET /api/payments/list` — список последних депозитов (для дашборда).
- ✅ `POST /api/payments/check` — проверяет конкретный депозит по блокчейну
  (TronGrid для TRX/USDT, TonCenter для TON), вызывается кнопкой "Проверить"
  из Mini App — принудительно, сразу.
- ✅ `POST /api/payments/worker` — **новое**: фоновая проверка ВСЕХ pending
  депозитов сразу + просрочка (`status: 'expired'`) всего, что старше
  `DEPOSIT_EXPIRY_MINUTES` (`lib/depositExpiry.ts`, по умолчанию 30 минут).
  Логика подтверждения платежа общая для `check.ts` и `worker.ts`
  (`lib/verifyDeposit.ts`), чтобы два пути не могли разъехаться.
- ✅ Дашборд на `/` — тестовое создание платежа, кнопка "Проверить оплату"
  прямо там же, таблица депозитов.
- ✅ SQL-миграция таблицы `deposits` (`sql/schema.sql`) + функция
  `increment_balance` для атомарного начисления баланса (`sql/increment_balance.sql`).
- ✅ `webapp/js/ui/depositModal.js` основного Mini App подключён к реальным
  `/api/payments/create` и `/api/payments/check` (заглушка `DEMO-` убрана).

### Настройка фонового воркера (cron-job.org)

1. Зарегистрируйся на cron-job.org (бесплатно).
2. Создай job: URL — `https://<твой-домен>.vercel.app/api/payments/worker`,
   метод **POST**, интервал — каждую 1 минуту.
3. В разделе заголовков (Headers) добавь `x-internal-token: <значение INTERNAL_API_TOKEN>`.
4. Без этого воркера проверка платежа произойдёт только если пользователь
   сам нажмёт "Проверить" — само по себе это не страшно (клиент и так
   пассивно опрашивает `check` раз в минуту, пока вкладка открыта), но
   именно воркер гарантирует проверку и просрочку даже если человек
   полностью закрыл Mini App.

### Правила минимальной суммы и комиссии

Больше не хардкод — редактируются в админ-вкладке основного Mini App
(раздел "Пополнение балансом"): по каждой валюте отдельно тип комиссии
(₽ фиксированная / % от суммы), значение комиссии и минимальная сумма
пополнения. Значения по умолчанию (пока админ ничего не менял) — в
`lib/rates.ts` (`FALLBACK`) и синхронизированы с `webapp/js/config.js`
(`DEFAULT_SETTINGS`) основного Mini App.

## Дашборд (`/`)

Приватная страница — при первом заходе просит `INTERNAL_API_TOKEN`
(тот же, что в переменных окружения), сохраняет его в `localStorage`
браузера и подставляет во все запросы заголовком `x-internal-token`.
Никакого отдельного логина/пароля пока нет — токен и есть пароль,
храни его как секрет.

Что можно делать:
- Создать тестовый депозит (валюта + сумма + произвольный тестовый
  `user_id`) и увидеть реальный сгенерированный адрес и разбивку суммы
  (курс / сумма по курсу / комиссия / итого к отправке).
- Посмотреть таблицу последних 20 депозитов из базы.

Это заменяет ручные `curl`-запросы для проверки, что деривация и расчёт
цены работают правильно, ещё до того как `check-payment` и реальный
Mini App будут подключены.

## Что впереди (следующий шаг — сообщи, когда дойдём)

1. **Свип** — перевод денег с одноразового адреса на мастер-кошелёк
   (с учётом TRX на газ для отправки USDT). Плюс кнопка вывода в
   дашборде, когда деньги реально начнут копиться. Пока не сделан —
   деньги лежат на одноразовых адресах, ты сам переводишь их себе вручную
   по мере надобности (приватный ключ выводится из seed по индексу
   `deposits.id`, см. "Модель безопасности" ниже).

### ⚠️ Перед тем как тестировать `check`, обязательно проверь

`sql/increment_balance.sql` предполагает конкретную структуру таблицы
`users` в основном проекте (колонки `avatar`, `orders` как `jsonb`,
`consent`, `balance`) — это списано с того, что использует
`webapp/js/api/profile.js`, но я не видел реальную DDL этой таблицы в
Supabase, поэтому нужно свериться самому перед запуском: открой
Supabase → Table Editor → `users` и сравни типы колонок с тем, что в
файле. Если что-то отличается — поправь `sql/increment_balance.sql` под
реальную структуру перед тем как выполнять его в SQL Editor.

### Установка новой функции начисления баланса

Открой Supabase → SQL Editor → вставь содержимое
`sql/increment_balance.sql` → Run (один раз, после проверки структуры
выше).

## Установка

```bash
npm install
cp .env.example .env.local
# заполни .env.local реальными значениями (см. комментарии в файле)
npm run dev
```

### Заполнение `.env.local`

- `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` — из настроек того же
  Supabase-проекта, что использует основной Mini App (Project Settings →
  API → `service_role` ключ, **не** `anon`).
- `TRON_HD_MNEMONIC` — сгенерируй новую 12-словную BIP39-мнемонику
  специально для этого проекта (например, через `bip39` в Node или
  любой офлайн-генератор) — **не используй мнемонику от личного
  кошелька**, чтобы в случае утечки пострадали только эти
  one-time-адреса, а не твои личные деньги.
- `TON_MNEMONIC` — отдельная 24-словная TON-мнемоника, тоже новая, тоже
  не от личного кошелька.
- `TRONGRID_API_KEY` / `TONCENTER_API_KEY` — бесплатная регистрация на
  trongrid.io / toncenter.com.
- `TELEGRAM_BOT_TOKEN` — тот же токен, что уже использует бот.
- `INTERNAL_API_TOKEN` — понадобится на шаге 2 (фоновый воркер), можно
  сгенерировать заранее: `openssl rand -hex 32`.

### Применение SQL-миграции

Открой Supabase → SQL Editor → вставь содержимое `sql/schema.sql` →
Run. Это создаёт таблицу `deposits` с полностью закрытым RLS (доступ
только через `service_role`, которым пользуется этот сервис).

### Деплой на Vercel

```bash
vercel
```
Затем добавь все переменные из `.env.local` в Vercel → Project Settings
→ Environment Variables (Production **и** Preview, если планируешь
тестировать на preview-деплоях).

## Модель безопасности — коротко

- Приватные ключи одноразовых адресов **не хранятся** — они каждый раз
  заново выводятся из seed по индексу (`deposits.id`), когда нужно
  что-то подписать (свип). Сам seed живёт только в переменных
  окружения Vercel.
- `SUPABASE_SERVICE_ROLE_KEY` обходит RLS полностью — значит все
  проверки прав доступа лежат на коде эндпоинтов, а не на базе.
  Именно поэтому `user_id` для любой операции берётся только из
  провалидированной Telegram `initData`.
- Таблица `deposits` не имеет ни одной RLS-политики для anon — значит
  из основного Mini App (который ходит в базу anon-ключом) её вообще
  не видно напрямую, только через API этого сервиса.

## Тестирование перед реальными деньгами

Прежде чем пускать в это настоящие USDT/TRX/TON — прогони весь цикл
(создание адреса → отправка → нахождение платежа → свип) на тестовых
сетях:
- TRON: **Nile Testnet** (тестовые TRX/USDT через кран/faucet)
- TON: **TON Testnet**

Только после того как весь цикл отработает на тестнете без сюрпризов —
переключай `TRONGRID_API_KEY`/`fullHost` и TON-эндпоинты на mainnet.
